For this codebase and time remaining:

**Polling**
- simplest recovery model
- weak demo UX
- bad fit for cursors/presence

**Postgres Changes**
- strong for durable note changes
- still need another mechanism for presence/cursors
- adds publication/policy setup

**Supabase Broadcast + Presence**
- minimal rework
- low-latency note notifications and cursors
- Presence directly handles connected users/activity
- existing HTTP API can remain the durable write path

**CRDT**
- best same-text collaboration semantics
- highest integration/debugging risk
- not justified for a one-hour extension

Recommendation:
- Postgres stays source of truth
- browser persists through existing API
- only after save succeeds, broadcast the saved note
- Presence for participant/activity
- Broadcast for cursors
- refetch current board after subscribe/reconnect to recover missed events.
